```sh
sw_vers; sysctl -n machdep.cpu.brand_string hw.physicalcpu hw.logicalcpu \
  hw.perflevel0.physicalcpu hw.perflevel1.physicalcpu

git clone --recurse-submodules https://github.com/libKriging/libKriging.git && cd libKriging
git checkout -b macos-m4-session-2 origin/master
```

| Dir | Options | Loops |

## 2. Decision of #456 part (b): GCD vs sequential vs libomp

The question: is a Grand Central Dispatch backend for `detail::parallel_for` worth
≈ 50 lines of Apple-only code and a CMake option? The relevant baseline is
**`build-seq`**, the default macOS build, not libomp.

- [ ] Create the branch `feat/parallel-for-gcd` from `origin/master`. Port **only** the
      GCD backend of `origin/feat/macos-gcd-loops` (b0c493e) into master's
      `src/lib/ParallelFor.hpp`: a `dispatch_apply` path when `__APPLE__` and OpenMP is
      not compiled in, no `LK_APPLE_OPENMP` option, no threshold change. A
      `-DLK_NO_GCD_LOOPS` compile switch for measurement only. Build it as `build-gcd`
      (default options, no `OpenMP_ROOT`). Full `ctest` must pass.
- [ ] Determinism: write a small check program (not committed, or under `bench/` if
      useful) linked against each build: fixed data (n = 500 and 1500, d = 4, fixed
      seed), fit `BFGS4`, LL / LMP / LOO with gradients at a fixed theta, predict with
      stdev and cov, simulate (fixed seed), Vecchia and Nystrom predict, NestedKriging
      fit; print every number with `%.17g`. Outputs of `build-gcd` vs `build-seq` must be
      **bitwise identical** (each loop writes disjoint outputs; reductions stay in a fixed
      order). Same comparison `build-omp` vs `build-seq` (expected identical too, #462).
      n must be ≥ the thresholds so that the parallel branches actually run.
- [ ] Per evaluation: `bench/bench-threads` (see `bench/thread-budget/README.md`),
      d = 4, n ∈ {100, 150, 200, 400, 800, 1500}: LL and LL + gradient, in `build-seq`,
      `build-gcd`, `build-omp`, `build-omp200`.
- [ ] Full fits: `bench/bench-fit-profile` at n ∈ {200, 500, 1000, 1500}, d = 4,
      `BFGS` and `BFGS4` (the default since T3), wall and CPU time, same four builds.
- [ ] Decision rule (to report against, not to apply): keep GCD if it is ≥ ×1.3 faster
      than `build-seq` on `BFGS4` fits for n ≥ 500, and never slower for n < 500 (no
      oversubscription with the multistart pool). Compare with `build-omp`: if libomp is
      as fast, the simpler answer may be to document/enable libomp instead (section 4).
- [ ] If GCD qualifies: open a PR `feat/parallel-for-gcd` → master with the numbers.
      Otherwise: comment on #456 with the numbers and propose to close it.
